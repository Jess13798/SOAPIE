**Lectura:**

- La búsqueda por **DNI** pasó de ~2,5 s a **decenas de milisegundos**.
- La búsqueda por **cuenta/historia** bajó a menos de 1 s.
- La búsqueda por **nombre** sigue siendo la más lenta, porque tiene que
  escanear los ~353k pacientes con un `LIKE '%texto%'` (comodín inicial), que
  **SQL Server no puede resolver con un índice**. No es un problema del código.

## 3. Por qué el nombre sigue lento y qué se puede hacer

`Pacientes` tiene un índice `Ind_apellido` sobre
`(ApellidoPaterno, ApellidoMaterno, PrimerNombre)`, pero un comodín al inicio
(`%texto%`) no puede usar el índice: se lee la tabla completa.

Opciones para acelerarlo (a decidir, ninguna aplicada aún):
1. **Priorizar hospitalizados**: en la búsqueda por nombre, correr primero la
  rama de pacientes con cama o estancia pendiente (esa tarda ~0,3 s) y
  devolverla si hay resultados; escanear todo solo si no hay. Hace rápidas las
  búsquedas del día a día, con el costo de no mostrar un paciente dado de alta
  cuyo nombre coincida con el de uno hospitalizado.
- **Índice de texto completo** (full-text) sobre el nombre: rápido, pero solo
  encuentra desde el inicio de una palabra y requiere crear un catálogo de texto
  completo en la base (cambio de esquema).
- **Aceptar ~2,5–3 s** solo cuando se busca por nombre.

> Nota: una columna calculada con índice **no** ayuda aquí, porque el comodín
> inicial (`%...%`) impide usar el índice igualmente.

## 5. Nota sobre el "sin servicio" en los resultados

El buscador devuelve el **servicio actual** así: primero la estancia pendiente de
cama (`LlegoAlServicio = 0` + facturación `IdEstado = 12`), y si no, la cama
ocupada. Si el paciente ya fue dado de alta o trasladado, aparece sin servicio
(aunque exista en el padrón). Es el comportamiento correcto para enfermería.

```
#    /api/pacientes/buscar (nombre, DNI, historia, cuenta).
node backend/scripts/medir-rendimiento.js

# Tests (no tocan la base)
npm test
```
